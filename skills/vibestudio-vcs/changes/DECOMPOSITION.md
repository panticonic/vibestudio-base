# semanticCommitMessage and summarizeChanges: decomposition

Both functions read one `vcs.compare` result (`compare`, usually `view: "local"`: protected main against the working
changes, so the changes are on the `theirs` side). They propose and describe; committing, merging and pushing stay with
the agent. Compare's own rule applies: a purpose is never synthesized from a diff. The only reasons offered are ones an
author recorded.

| Part                                                              | Form                                                           | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reduce a compare result to the changes the source side makes      | crisp: `summarizeChanges/digest.ts`                            | Exact reading of coordinates and aspects: added (no base path), deleted (no source path), moved (paths differ), edited (content aspect), mode-changed; files grouped by repository (first two path segments); recorded intents joined to repositories by the coordinates each intent covers. A compare result is far too large for the executor's context; the digest is small and typed. The generated `summary` strings are presentation only (a deleted file's reads "adopt file file:<id>") and are never parsed. |
| One line that says what the changes do                            | its own function, `commitSubject` (generated text)             | Meaning-to-prose: needs the executor. One `problem?` retry, as the checked-stage pattern says.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Check the line                                                    | crisp: `problemWith` in `commitMessage.ts`                     | Length (72), single line, names something the digest shows. A second failure is returned as a warning, never replaced by crisp text.                                                                                                                                                                                                                                                                                                                                                                                  |
| Does a recorded intent give a reason                              | its own function, `givesReason` (`readout: decision`, boolean) | The commit `intent` argument is for a reason that is not clear from the request. Telling "Fix the failing test" (what) from "Stop the loader retrying forever because it hid the 503 outage" (why) is a finite judgment over meaning. Only `stated` intents are candidates: `trigger` restates the request and `mechanical` is derived from the effect. The intent is copied verbatim; the function never writes one.                                                                                                 |
| One sentence per repository                                       | its own function, `describeUnit`                               | Same kind of work as the subject, per unit; independent, so run in parallel.                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Headline of the summary                                           | reuses `commitSubject`                                         | The net effect in one line is the same text a commit subject is.                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| `state` (ready, decisions-needed, conflicts) and `attention` list | crisp, in `summarize.ts`                                       | Compare says them exactly: `counts.conflict`, `resolution.complete`, `counts.composed`, and the coordinate statuses. Judging them would only add error.                                                                                                                                                                                                                                                                                                                                                               |
| Carrier `summarizeChanges.nl`                                     | one instruction                                                | Hosts the callable folder. `summarizeChanges.commitMessage(compare)` is `semanticCommitMessage`; `summarizeChanges.summarize(compare)` is `summarizeChanges`.                                                                                                                                                                                                                                                                                                                                                         |

## Measurement

`cases.jsonl` pairs each comparison scenario with a commit case and a summary case (one split per scenario). One
scenario is a comparison captured from a live instance (`live-capture`: an added, a deleted, an edited and a moved file);
the others are built in the same shape from repository paths and commit-style intents. Commit quality: one line of at most 72
characters, naming the change, and the right `intent` (verbatim reason or null). Summary quality: exact `state` and
`attention`, and sentences that name the repository or its files. Gates: 0.85 on validation and on the locked test split, per function.

## Status: not ported

SKILL.md does not call this function: the gates are not met. Evidence, on the executor (LFM3 1.7B Q8_0, `pnpm natlang:eval`):
the first sampled case (`all-resolved:summary`, suite settings 4 turns, 192 tokens per turn) failed in `describeUnit` with
"quiesced: episode turn, token, or wall-clock budget exhausted" and took 20 minutes on the shared server, so quality 0 on it. A full
validation run (8 cases) did not complete: with the case watchdog removed it stalled with no request in flight after 85 minutes
(root cause not found), and full runs on the shared machine were not feasible afterwards. The recorded failure is for the generated-text functions (`commitSubject`, `describeUnit`); the exact digest and its tests stand. The suite, cases and
checks stay; a later run on a quieter machine, or an instruction that lets the model finish in few turns, decides whether it ports. Until then the agent
performs this procedure itself.
