# Discover intent before using installed local capabilities

| Existing mechanism | Use |
| --- | --- |
| Baseline `intent-discovery.ts` and Host `docsService` | Begin with an underspecified user purpose and owned references. Search actual role-filtered service documentation, then obtain the exact current schema for any selected effect. A known method from old instructions or a search label cannot stand in for an installed exact contract. |
| Installed `skills/sandbox/help` search policy | The keyword stage follows the installed help workflow scope. Production catalog search and exact registry descriptions stay separate from choosing a local effect. |
| Runtime `workspace.listSkills` and `workspace.readSkill`, VCS native status and read, bounded scratch, and `runtime.listEntities` | Perform only exact local reads relevant to the goal. Separate installed instructions, current semantic state, a retained note, and an exact runtime entity. Two sources need two independent observations. Bound output and prevent retargeting. |
| Host trajectory and managed System Testing runner | The exact user goal is the root input. Keep expected routes and checks outside model context. Verify actual search-reference bindings, native scoped readback, retained absence, and any authorized private note. Source only uses real production registry behavior and injected local workspace ports. |

1. Inspect the owned working notice for candidate references and derive likely needs from the unchanged goal. Names in the notice identify scopes without carrying expected tool IDs.
2. Derive useful catalog phrases from the user’s goal. Search, describe any relevant hits, and choose only the smallest set of verified actions that jointly answers the request.
3. Inspect the selected exact native scopes, checking that historical or absent receipts cannot stand in for a current action or deployed result. Keep a private note only if explicitly requested.

## Semantic capability selection and exact native values

`searchRelevantIntent.nl` chooses exact method IDs for the user goal. It does not reproduce raw queries/hit arrays; those are already recorded in the trace. `chooseIntentActions.nl` and `concludeIntentReview.nl` remain typed natural-language policy and answer functions. The five former service passthrough lambdas (`readIntentNotice`, `searchIntentCatalog`, `describeIntentCapability`, `inspectIntentEvidence`, `stageIntentNote`) are TypeScript plumbing with explicit native service imports; empty NL serviceScopes prevent direct service exposure to policy lambdas. `describeIntentSelection.ts` joins selected IDs to exact native contract values, so model-generated descriptions cannot silently replace installed facts. No method selection or action plan is scripted in TypeScript.
