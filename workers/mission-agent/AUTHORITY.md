# Mission lead and task executor authority

MissionAgent extends the ordinary AiChatWorker vessel and uses the same
reviewed standard tool capabilities. Its additional `mission_control` tool
offers a finite set of app-shaped operations through the exact Mission Control
service binding. Tool execution binds RPC to the admitted native invocation;
the offered registry cannot turn into a second execution authority channel.

`installTaskAutomation` seals this installed vessel's source state, effective
version, class and object key into the canonical Missions charter. It never
asserts an arbitrary runtime image or mints authority. MissionsDO owns
installation, acquisition, cadence, run admission and outcomes. Fresh runs
read the current task through ordinary domain operations and use normal
approvals for their work.

The top-level lead uses a stable conversation and entity identity. Task agents
use the same vessel and native tool registry, with distinct task automation
identities. Project repository associations express intended scope rather
than privileges. Cards, view state and execution controls share the human UI's
domain operations and revision rules.
